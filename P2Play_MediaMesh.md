# P2Play и MediaMesh — децентрализованный торрент-каталог + стример: требования и роадмап

Nov 21, 2026 · @freetushkan

## Цель и принципы

Цель: сделать all-in-one сервис по образцу Android-приложения TorrServe. Он качает, стримит и ведёт каталог торрентов. Каталог распространяется через сам BitTorrent и не зависит ни от трекеров, ни от центральных серверов. Названия: P2Play — приложение (ядро, демон, интеграция в pPlay), MediaMesh — протокол и сеть, через которую распространяются списки. MediaMesh не привязан к P2Play: совместимый клиент может написать кто угодно. Серверная часть P2Play ниже называется ядро.

Принципы:

- Без центра. Ни один узел, домен или ключ не нужен системе для работы. Трекеры — только источник данных для граббера, не транспорт.

- Открытость. Любой может выпустить свой список (базу) под своим приватным ключом. Клиент сам выбирает, на какие списки подписаться.

- Проверяемость. Всё, что можно проверить криптографически (infohash ↔ метаданные, подпись ↔ ключ), проверяется. Доверие нужно только к выбору списков.

- Совместимость. HTTP API условно совместим с TorrServer, поэтому Lampa, pPlay и прочие клиенты TorrServer работают без доработок.

- Разносимость. База, качалка и стример работают в одном процессе, но любую часть можно вынести на удалённый сервер. Клиент (pPlay) ходит в ядро по API — локальное или удалённое.

- Кроссплатформенность. Те же цели, что у pPlay: Linux, Switch, PS4, PS5, Android TV. Позже ядро встраивается в pPlay как внутренний сервис.

Вне рамок первых версий: постеры и описания, поиск по метаданным фильмов, DLNA, веб-интерфейс сложнее служебного.

## Архитектура

Все роли выполняет одна кодовая база — ядро. Клиенты ходят в него по HTTP, релизёр — это то же ядро с ключом, а узлы между собой общаются только через BitTorrent.

Ядро состоит из двух независимых модулей поверх одной сессии libtorrent. Каталог (MediaMesh): указатели в DHT, синхронизация и проверка списков, индекс, поиск, публикация. Стример: раздачи медиа, HTTP-стрим, API TorrServer, прогресс просмотра. Каталог от стримера не зависит: ядро запускается и без стримера, как узел каталога. Такой узел качает и раздаёт только торренты списков, медиа не качает и отдаёт по HTTP только маршруты каталога. Это база для поиска в чужих клиентах, в первую очередь в плагине TorrServer Silo (см. раздел API), и лёгкий способ круглосуточно раздавать списки на сервере. Располагается рядом с Silo или на другом хосте.

Ядро — модуль без платформенного кода. Каталог данных, лог (через обратный вызов), краш-хендлеры, запрет сна на время стрима (p2play_active_streams()) и поведение платформы даёт хост. Внутри pPlay хост — pPlay (его Platform, CrashLog, лог, каталоги). Автономный хост (src/app) — обвязка pPlay для приложения без экрана: краш-логи всех платформ, символы в CI, запрос выхода и фон на Switch, тики воспроизведения и выход через систему на PS4. Правило: любая платформенная доработка берётся из pPlay целиком, а не собирается заново.

**Текстовая расшифровка схемы архитектуры:** pPlay и Lampa/другие клиенты обращаются к ядру P2Play по HTTP API локально или удалённо. В ядре выделены HTTP API (Silo-схема и MatriX-совместимый shim), пользователи и прогресс (SQLite, отдельно на каждого), движок (стрим с Range и RAM-кэш), каталог (реплика в SQLite FTS5 и поиск), списки (подписки, мета-списки, проверка подписей, BEP 44/46). Отдельный Python-граббер получает данные из трекеров и архивных дампов и передаёт NDJSON релизёру. Релизёр — то же ядро в режиме публикации, с приватным ключом Ed25519, работающий через SOCKS5 или WireGuard. Он выпускает подписанные версии в сеть MediaMesh поверх BitTorrent без обязательных трекеров; в сети используются DHT (BEP 5, 44, 33), рои раздач и списков, рой каталога и расширение mediamesh (BEP 10).

архитектура · ядро, клиенты, релизёр, граббер

Варианты размещения:

| Вариант | Где ядро | Кому подходит |
| --- | --- | --- |
| All-in-one | внутри pPlay (библиотека) | консоль или ТВ-приставка без сервера |
| Локальный демон | отдельный процесс на том же устройстве | Linux, Android TV; как сейчас TorrServe на Android |
| Удалённый сервер | systemd-сервис на сервере | несколько клиентов и пользователей, круглосуточная раздача списков |
| Разнесённый | каталог на одном ядре, стрим на другом | слабое устройство: ищет на сервере, качает само |
| Релизёр | ядро с --publish и ключом, за прокси или туннелем | издатель списка |

Граббер — единственная часть, которая вообще ходит на трекеры. Он отделён от ядра и нужен только издателю.

Поставки. Из одного ядра собираются:

| Платформа | Поставка | Что умеет |
| --- | --- | --- |
| PS4, PS5, Switch | модуль в pPlay | поиск, списки, стрим внутри плеера |
| Android | модуль в pPlay | то же + открывает ссылки torrs:// |
| Android | отдельный APK P2Play | поиск и стример без плеера; из результата поиска делает ссылку torrs:// и открывает её в pPlay или другом приложении |
| Linux | модуль в pPlay | как на консолях |
| Linux | отдельный AppImage P2Play | поиск и стример |
| Silo | плагин + демон на localhost | плагин — интерфейс децентрализованного поиска; вся логика поиска в демоне (узел каталога), общение через его REST |

Следствия:

- Ядро — статическая библиотека на C++ с узким C API для pPlay (запуск, остановка, адрес своего HTTP-сервера). Внутри pPlay оно тоже поднимает HTTP на localhost: плеер и интерфейс работают с ним так же, как с внешним демоном. Демон, APK и AppImage — обёртки вокруг той же библиотеки.

- torrs:// — формат TorrServer (TorrsHash): base62 от zlib(infohash + поля title, poster, tracker, category, size). Все поля есть в записи списка, поэтому ядро умеет и строить такие ссылки, и разбирать их. Эталон: internal/torrshash в Silo и TorrsHash.kt в TorrServe для Android.

- Отдельные APK и AppImage — полное ядро с API TorrServer, так что ими можно пользоваться и из Lampa. Тестовый APK p2spike — заготовка отдельного APK: сервис с ядром там уже есть.

- Интерфейс отдельных поставок — один веб-интерфейс, который отдаёт само ядро: в APK — во WebView, в AppImage — в браузере или своём окне, с сервера — по адресу.

- Данные на Android (конфиг, логи, загрузки) — в /sdcard/.p2play с доступом ко всем файлам, как .pplay у pPlay; без доступа — Android/data/<пакет>/files.

## Модель данных

Список — это ключ ed25519. Версия списка — это подписанный указатель в DHT на обычный торрент с данными. Имя, домен или сервер списку не нужны: его идентифицирует публичный ключ.

| Сущность | Где живёт | Содержимое | Проверка |
| --- | --- | --- | --- |
| Ключ списка | у релизёра (приватный), у всех (публичный) | ed25519, 32 байта | — |
| Указатель | BEP 44 mutable item, salt mediamesh.v1 | seq, ih (infohash манифеста), короткое имя; до 1000 байт | подпись ключа, рост seq |
| Манифест | manifest в торренте версии (v2) | имя, описание, версия схемы, seq, список сегментов и паков с хэшами, словарь тегов, политика переиздания | подпись ключа внутри манифеста |
| Сегмент записей | records/seg-NNNNNN.zst | пачка записей и удалений | merkle-дерево v2 |
| Пак описаний | media/desc-NNNNNN.zst, один на сегмент | тексты описаний подряд | merkle-дерево v2 |
| Пак постеров | media/poster-NNNNNN.bin, один на сегмент | WebP-картинки подряд | merkle-дерево v2 + sha256 картинки в записи |
| Запись | в сегменте | обязательно только infohash и название; опционально: размер, число файлов, дата создания или изменения торрента (без неё — дата появления в списке, а без неё — дата сборки списка), теги, список файлов, трекеры, ссылки (смещение + длина) на описание и постер в паках | по запросу — BEP 9 по infohash |
| Удаление | в сегменте, тип tombstone | infohash + дата | — |

Правила:

- Сегменты и паки только дописываются. Новая версия = старые файлы + новые. В торренте v2 у неизменного файла тот же pieces root, поэтому клиент качает только новое.

- Медиа качается по требованию. Из выбранных шардов клиент качает слой индекса (см. ниже), а из паков — только нужный диапазон байтов, тем же механизмом приоритета кусков, что и стрим. Постеры и описания подгружаются, когда карточка попадает на экран, и кэшируются. Опция «зеркало медиа» (по умолчанию выключена) заставляет клиента скачать все паки выбранных списков и раздавать их другим, с лимитом по диску. Рассчитана на демон на ПК или сервере; на консолях её нет. Паки нужны, потому что миллион отдельных файлов раздул бы метаданные торрента.

- Переиздание определяет релизёр. Когда выпускать снапшот (один сегмент без удалённых записей и неиспользуемого медиа), решает релизёр и пишет политику в манифест. По умолчанию снапшот выпускается, когда сегментов больше 64 или удаления составляют больше 20% записей (цифры — стартовые, для проверки).

- Жёсткие лимиты задаёт клиент. Максимум сегментов, размер записей, длина описания, размер постера. Версию, которая нарушает лимиты, клиент не принимает и остаётся на предыдущей.

- Теги свободные. Список может принести свой словарь тегов в манифесте: отображаемое имя, синонимы, группа (жанр, качество, язык). Клиент склеивает теги разных списков по написанию и синонимам.

- Трекеры — на выбор релизёра. Поле опциональное и только ускоряет поиск пиров: DHT работает и без него.

- Запись проверяема сама по себе. Название, размер и файлы сверяются с метаданными по BEP 9. Субъективны только теги, описание и постер.

- Локальная реплика. Клиент сливает подписки в одну SQLite с FTS5 (название, теги, описание — если скачано). У каждой записи хранится, из каких списков она пришла.

- Оценка объёма: около 150 байт на запись без медиа, то есть 1 млн записей ≈ 150 МБ до сжатия. Постер WebP до 30 КБ даёт до 30 ГБ на миллион: целиком их держат релизёр и зеркала медиа, обычный клиент — только просмотренное. Цифры приблизительные, их нужно проверить на реальном дампе.

Сколько данных держит клиент. Даже «имя + magnet» на миллионы записей — десятки мегабайт, поэтому список делится на слои и шарды, и клиент берёт только то, что влезает в его бюджет диска.

| Слой | Содержимое | Кто держит |
| --- | --- | --- |
| Индекс | infohash, название, дата; ориентир — 40–50 байт на запись сжатыми, 1 млн ≈ 50 МБ | подписчик — только выбранные шарды |
| Детали | размер, файлы, теги | по требованию или целиком — настройка клиента |
| Медиа | описание, постер | по требованию; целиком — релизёр и зеркала |

- Шарды. Релизёр делит список по группам тегов (фильмы, сериалы…) и по времени; манифест перечисляет шарды с размерами. Клиент ставит список целиком или только нужные шарды, с лимитом по диску на список.

- Поиск без реплики. Клиент с маленьким диском ищет через ядро на сервере (разнесение каталога и стримера уже заложено). Позже — сообщение search расширения mediamesh к пирам, которые держат список целиком и согласились отвечать (опция, по умолчанию выключена).

Данные пользователя живут отдельно и никуда не распространяются: пользователи и токены, библиотека (добавленные торренты), прогресс просмотра по файлам, подписки.

## Протокол распространения

Всё строится из стандартных BEP плюс одно собственное расширение BEP 10. Трекеры не используются нигде.

| BEP | Зачем |
| --- | --- |
| 5 — Mainline DHT | поиск пиров для всего: контента, манифестов, каталога списков |
| 9 — ut_metadata | получение метаданных по magnet и проверка записей |
| 10 — Extension Protocol | расширение mediamesh: обмен списками и их версиями между нашими клиентами |
| 44 — данные в DHT | подписанный указатель «текущая версия списка» |
| 46 — обновление торрентов через DHT | формат указателя и magnet xs=urn:btpk:<pubkey>, чтобы список можно было передать одной ссылкой |
| 52 — BitTorrent v2 | пофайловые merkle-деревья: дешёвые инкрементальные версии |
| 33 — DHT scrape | оценка числа держателей списка для рейтинга |
| 51 — sample_infohashes | опциональный источник данных для релизёра (обход DHT) |

Выпуск версии и каскад:

- Релизёр собирает новый сегмент, манифест и торрент v2, и начинает его раздавать.

- Публикует в DHT указатель с seq + 1 (BEP 44 put).

- Рассылает подписанный указатель пирам в рое каталога (расширение mediamesh).

- Клиент, получивший указатель любым путём, проверяет подпись и seq, качает манифест и новые сегменты. Приняв версию, он сам пересылает указатель своим пирам и раздаёт версию.

- Подписчики периодически перепубликуют тот же подписанный указатель в DHT. Список живёт, даже если релизёр ушёл насовсем: новых версий не будет, но последняя остаётся доступной.

Расширение mediamesh (BEP 10), черновик сообщений:

| Сообщение | Содержимое | Когда |
| --- | --- | --- |
| have | список пар (pubkey, seq), которые держит пир | при рукопожатии |
| get | pubkey, который запрашиваем | у пира свежее seq или незнакомый список |
| item | подписанный указатель целиком (как в BEP 44) | ответ на get и push при новой версии |

Подписанный указатель проверяется без DHT, поэтому его можно безопасно передавать через недоверенных пиров. DHT — запасной путь и первая точка входа, расширение — быстрый путь.

Релизёр за прокси: в libtorrent есть SOCKS5 с UDP ASSOCIATE (DHT и uTP идут через прокси). Ещё один вариант — запуск в netns с WireGuard/AmneziaWG. За SOCKS5 входящих соединений нет, но это не мешает: релизёр сам соединяется с пирами, а дальше версию раздают подписчики.

## Каталог списков и рейтинг

Клиент узнаёт о списках через общий «рой каталога», а рейтинг списка = оценка числа клиентов в рое этого списка.

- Рой каталога. Фиксированный infohash sha1("mediamesh.v1/directory"). Каждое ядро анонсируется в него через DHT, подключается к нескольким пирам и получает от них have — известные им списки. Ни сервера, ни адреса для этого не нужно.

- Рой списка. Стабильный infohash sha1("mediamesh.v1/list/" + pubkey), не зависящий от версии. В него анонсируется каждый подписчик.

- Рейтинг. BEP 33 scrape по рою списка даёт оценку числа подписчиков без подключения к ним. Точное число не нужно: для сортировки хватит порядка.

- Карточка списка в клиенте: имя, описание, отпечаток ключа, число записей, дата последней версии, оценка числа подписчиков. Имя не уникально, идентификатор — только ключ.

- Подписка. Из каталога или по magnet-ссылке на список (BEP 46). Для первого запуска нужен хотя бы один популярный список, иначе поиск пуст.

- Мета-списки. Особый список, в котором вместо записей о торрентах лежат ключи других списков с короткой аннотацией. Подписка на него подписывает на всё входящее; отдельные списки можно отключить. Вложенность ограничена одним уровнем, чтобы не было циклов. Комплектный мета-список решает проблему холодного старта.

Ограничение: число подписчиков можно накрутить анонсами с множества адресов (особенно IPv6). Защита — считать уникальные подсети (/24, /64) по выборке get_peers и добавлять локальные сигналы (сколько записей списка нашли живых пиров). Рейтинг — эвристика, а не доказательство, и UI должен это честно показывать.

## API

Основной API повторяет REST-схему ветки silo TorrServer и дополняет её прогрессом просмотра и каталогом. Для Lampa и текущего pPlay нужен слой совместимости с MatriX.

Что есть в источниках (проверено по коду на дату документа):

- Silo (ветка silo, переписанный с нуля TorrServer). README называет его ранней разработкой, но по личной проверке он уже качает и отдаёт видео. Замеченная деградация — нет прогресса по файлам; его планируется вернуть отдельным PR в Silo по мотивам MatriX. Маршруты под /api, пользователи с токенами (Authorization: Bearer, ?token= для плееров, cookie silo_token). Индексы файлов с 0. Просмотр — только флаг viewed на файл, ставится автоматически при стриме.

- MatriX (ветка master, версии MatriX.1xx). JSON-действия в POST /torrents и POST /viewed. У viewed есть поле timecode (позиция в секундах), оно сохраняется при настройке TrackTimecode. Индексы файлов с 1.

| Группа | Маршруты | Откуда |
| --- | --- | --- |
| Торренты | GET/POST /api/torrents, GET/DELETE /api/torrents/:hash, PUT /api/torrents/:hash/meta, POST /api/torrents/:hash/wake, POST /api/torrents/:hash/files/:idx/preload, GET /api/torrents/:hash/cache, GET /api/torrents/:hash/peers | Silo |
| Стрим | GET /api/stream/:hash/:fileIdx (Range); плейлист m3u — из MatriX | Silo |

| Каталог | GET /api/catalog/search?q=&cat=&limit=, GET /api/catalog/:infohash (запись + списки-источники) | новое |

| Совместимость MatriX | GET /echo, `GET /stream?link=&index=&play | stat |

Правила прогресса:

- Эндпоинт и поля прогресса проектируются одновременно с PR в Silo, чтобы у P2Play и Silo они совпадали. Прогресс хранится на пользователя и файл: position, duration, viewed, updated_at.

- viewed ставится сам, когда position / duration превышает порог (настройка, по умолчанию 90%). Ручная отметка через эндпоинты Silo тоже работает.

- Шим MatriX переводит номера файлов и timecode в position. Номера как у оригиналов: MatriX — с 1 по отсортированному списку всех файлов (заглушки .pad считаются), Silo — индекс файла в торренте с 0. Это разные числа одного файла: клиент должен работать с сервером через один API (pPlay смешивал списки обоих — файлы двоились со сдвигом на один).

- Авторизация. Пользователи одни на оба API, каждый API спрашивает их как оригинал:

- Вход обязателен на обоих API, учётные данные одни: /api (Silo) — токен, MatriX — Basic (WWW-Authenticate). Хранилище учёток, библиотеки и прогресса общее, номера файлов у каждого API свои (сдвиг учтён).

- Пока у владельца (owner) нет пароля, первый вход как owner с паролем задаёт его — через клиент Silo или через Basic из pPlay и Lampa (на консоли задать его больше негде). Маршруты, которые TorrServer оставляет открытыми (/stream с play или m3u, /play, /playlist), играют известный торрент без входа, как там. APK ходит к своему серверу токеном владельца из его auth.json.

- Разнесение: у клиента два адреса — «каталог» и «стример». По умолчанию это одно ядро, но можно искать на сервере, а качать локально, и наоборот.

Схема Silo — основа маршрутов. Пока Silo меняется, P2Play держит свой OpenAPI-файл, снятый с конкретного коммита, и синхронизируется с апстримом вручную. Каталог, списки и публикация — собственные группы маршрутов, с Silo они не пересекаются; позже их можно предложить в Silo как плагин. Шим MatriX нужен с первого этапа, пока Lampa и pPlay работают с MatriX.

Плагин для Silo. Плагины Silo пишутся на JavaScript и работают в goja (internal/plugin). Им доступны добавление торрентов (torrent.add), чтение их файлов (torrfs), свои HTTP-маршруты и страницы, исходящий HTTP и хранилище «ключ-значение»; DHT, ed25519, расширений BEP 10 и полнотекстового индекса нет. Решение: плагин — интерфейс поиска и списков, он ходит в REST демона на localhost (адрес в настройках плагина), а выбранная раздача уходит в Silo через torrent.add. Вся логика MediaMesh — в демоне (узел каталога, стример не нужен). Правок в Silo не требуется. Реализация MediaMesh на Go внутри Silo не планируется, но спецификация должна позволять написать её без кода ядра.

## Стек и платформы

Ядро пишется на C++ с libtorrent-rasterbar 2.0: на этом стеке есть путь на все цели pPlay. TorrServer (и MatriX, и Silo) написан на Go с anacrolix/torrent, а Go не собирается под Switch, PS4 и PS5. Поэтому из TorrServer берётся схема API и логика стрима, а не код.

| Библиотека | Зачем |
| --- | --- |
| libtorrent-rasterbar 2.0 | движок; в нём уже есть DHT, BEP 9/10/44/51/52, SOCKS5, свои расширения и ed25519 для BEP 44 |
| Boost (asio, beast, json) | сеть, HTTP-сервер API, JSON; только заголовки |
| SQLite + FTS5 | библиотека, прогресс, локальная реплика каталога и поиск |
| zstd | сжатие сегментов |
| OpenSSL / mbedTLS | TLS для API и скачивания .torrent по https с проверкой сертификатов по поставляемому cacert.pem |

| Платформа | В каком виде | Особенности |
| --- | --- | --- |
| Linux x86_64 / arm64 | демон (systemd), сервер, релизёр | эталонная платформа для тестов |
| Android TV arm64 / armv7 | сервис внутри pPlay или отдельно | NDK; фоновая работа через foreground service |
| Switch | библиотека внутри pPlay | devkitA64 + libnx; без mmap → posix_disk_io или RAM-кэш; в спящем режиме сокеты рвутся; в applet-режиме мало памяти |
| PS4 / PS5 | библиотека внутри pPlay | те же тулчейны и portlibs, что у pPlay; на PS5 библиотеки грузятся из каталога pplay |

Сборка — через GitHub Actions, как у pPlay. Рецепты libtorrent, boost, sqlite и zstd добавляются в твои форки portlibs/pacbrew-repo. Работает ли libtorrent на консолях вообще, не проверено, поэтому это первая задача роадмапа.

Граббер живёт только на сервере, поэтому его можно писать на чём удобно, например на Python. На выходе он даёт NDJSON с записями для POST /api/publish/:pubkey/records.

Граббер и релизёр на консолях не нужны, поэтому им доступен любой стек ПК и сервера, в том числе статически слинкованный Qt (с GPL-3.0 совместимо). Граница: ядро и формат MediaMesh — библиотека без Qt, общая с консолями; Qt — только в оболочках серверных инструментов (GUI релизёра, сетевой клиент и расписание граббера). Решение принимаем к этапу 3 (релизёр) и 6 (граббер); для парсеров трекеров Python остаётся альтернативой.

## Граббер и формат импорта

Граббер — отдельная серверная утилита: собирает данные с трекеров и дампов, приводит их к одному формату и отдаёт релизёру. Формат импорта совпадает с записью списка, поэтому файл, собранный вручную или чужим скриптом, релизёр принимает так же.

Конвейер:

- Источник. Адаптер на каждый тип: дамп рутрекера (свой XML или HTML, богат данными), дамп рутора (JSON, тоже подробный), «грязные» строковые дампы (нужна предобработка; трекеров в них нет, часто попадается не медиа — такие записи идут с меткой Other), RSS, страницы или API трекера. Адаптер помнит, где остановился (id или дата), и каждый следующий запуск добирает только новое. Образцы дампов — когда дойдём до этапа 6.

- Нормализация. Infohash в hex нижним регистром, название, размер, число файлов. Категории трекера превращаются в теги по таблице соответствий, которую ведёт релизёр.

- Дедупликация по infohash. Если одна раздача пришла из нескольких источников, поля берутся из источника с большим приоритетом.

- Обогащение (по желанию). Недостающие размер и файлы — через BEP 9. Постер скачивается и ужимается до WebP (стартовый лимит — 300 px по ширине, 30 КБ). Описание очищается от разметки и обрезается по лимиту (стартовый — 2 КБ).

- Выход. NDJSON, одна запись на строку; постеры лежат рядом файлами с именем по sha256.

- Публикация. Релизёр принимает пачку (POST /api/publish/:pubkey/records или p2play publish --import) и выпускает версию по своей политике: по расписанию или когда накопилось N записей.

Запись импорта (обязательны только ih и name; date — дата создания или изменения торрента, если источник её знает):

```json
{"ih": "<40 hex, v1>", "name": "Название раздачи", "size": 4294967296, "files": 12,  
 "ih2": "<64 hex, v2>", "date": "2026-11-20", "tags": ["сериал", "1080p", "русский"],  
 "desc": "Описание без разметки", "poster": "sha256:<64 hex>",  
 "file_list": [{"p": "S01/E01.mkv", "s": 357913941}], "trackers": ["udp://..."], "src": "<источник>:<id>"}
```

Правила:

- Граббер ходит в сеть через тот же туннель, что и релизёр, и соблюдает лимиты запросов источника. Приватного ключа он не видит.

- Какие поля попадают в список (site, trackers, src, desc, poster, file_list), решает релизёр в настройках списка; лишнее отбрасывается при импорте.

- Трекер в записи — два независимых опциональных поля: site — метка трекера как сайта (rutracker, rutor, …), и trackers — конкретные URL анонса. Если источник не известен, site = Other. По метке клиент фильтрует и показывает источник, анонсы уходят в magnet.

- Описания и постеры с трекеров часто чужие авторские материалы. Брать ли их, решает издатель списка, и отвечает за это тоже он.

- Стек свободный (Python удобен для парсеров), запуск — systemd-таймер на сервере релизёра.

Нефункциональные:

- Асинхронность. Синхронизация, индексация и слияние списков внутри pPlay не должны вызывать задержек кадров: отдельный поток и низкий приоритет, пауза во время воспроизведения по настройке.

- Ресурсы. На консоли лимит памяти ядра задаётся явно, подписки можно ограничить по размеру.

- Безопасность. Проверка подписей на каждом указателе и манифесте. Лимиты на размер и число сегментов, чтобы список не мог забить диск. Проверка TLS везде. Приватный ключ не покидает релизёр.

- Версионирование протокола. Версия схемы в манифесте и в сальте (mediamesh.v1). Неизвестные поля игнорируются.

- Спецификация отдельно от кода. Форматы и сообщения описаны в своём документе, чтобы совместимые клиенты мог написать кто угодно (например, плагин для TorrServer).

## Роадмап

Без дат: этап считается законченным, когда выполнено условие справа. Этап 0 — самый рискованный: если libtorrent не заведётся на консолях, консоли работают только с удалённым ядром, а этап 5 отпадает.

**Текстовая расшифровка схемы этапов:** Этап 0 — спайк libtorrent на консолях (Linux, Switch, PS4, PS5), проверка magnet → видео на Switch и PS5. Этап 1 — ядро-стример (движок, RAM-кэш, библиотека, MatriX shim, демон), условие: Lampa и pPlay работают вместо TorrServer. Этап 2 — API по схеме Silo (REST, пользователи, прогресс), условие: прогресс с одного клиента виден на другом. Этап 3 — списки (формат, релизёр, подписка, каскад, прокси), условие: версия от релизёра через прокси скачивается и без релизёра. Этап 4 — каталог списков и UI (рой каталога, рейтинг, поиск и списки в pPlay), условие: новый клиент без ссылок находит и ставит список. Этап 5 — ядро внутри pPlay (all-in-one на консолях и Android TV), условие: синхронизация во время просмотра без задержек кадров. Этап 6 — граббер (адаптеры трекеров и дампов, NDJSON в релизёр), условие: список пополняется автоматически по расписанию.

роадмап · 7 этапов с условиями перехода

Этапы 2 и 3 можно вести параллельно. Если пустой каталог мешает тестам этапа 4, простой импорт архивного дампа из этапа 6 можно сделать раньше.

Узел каталога и плагин для Silo появляются вместе с поиском, на этапе 3; ссылки torrs:// — там же. Модуль каталога с этапа 1 пишется независимым от стримера. Отдельные APK и AppImage с поиском — на этапе 4, вместе с интерфейсом каталога; модуль в pPlay — на этапе 5.

PS5: payload не знает «уже запущено», повторный запуск поднимал второй сервер рядом с первым. Как в pPlay (его порт 9095), работающий сервер держит локальный UDP-порт 9097; система освобождает его вместе с процессом. Повторное открытие иконки просит сервер завершиться (через 10 с — kill), следующее запускает новый. Поиск процесса по имени потока не годится: завершённый payload остаётся в списке процессов, пока родитель его не заберёт.

Что выяснилось на этапе 0:

- Кусок «есть» раньше, чем он лежит в файле. В libtorrent 2.0 кусок считается скачанным после проверки хэша, а запись на диск идёт позже. Читать файл напрямую нельзя: стрим идёт через read_piece(). Логичный следующий шаг — свой disk_interface: он же даст режим «только RAM», как у TorrServer.

- PS5 почти нативный FreeBSD: не хватило только getrandom, заменён на arc4random_buf.

- Switch libtorrent не знает: добавлена явная ветка платформы (без mmap и fallocate, случайные байты из ядра через randomGet). В libnx нет sys/uio.h, IPv6, pipe и socketpair: добавлены заглушки в compat/, а asio будит свой цикл через пару loopback-сокетов (патч Boost) вместо pipe(). Интерфейсы и маршруты не перечисляются: libtorrent слушает 0.0.0.0, как на Android 7+.

- PS4 — главный риск этапа. В OpenOrbis заголовки musl с константами Linux, а ядро FreeBSD. pPlay уже оборачивает часы и флаги send/recv; для asio добавлены sendmsg/recvmsg. На деле риск меньше: musl в OpenOrbis уже приведён к FreeBSD (errno, O_NONBLOCK, макросы ioctl), не хватало FIONBIO/FIONREAD, sysctl и __cxa_thread_atexit_impl. asio работает через select (kqueue выключен), сокеты слушают 0.0.0.0. Проверка на консоли впереди.

- Проверка без CI. PS4 — тулчейн OpenOrbis v0.5.4 с GitHub (сборка и линковка). Switch — clang с заголовками newlib и libnx (только компиляция). Серверы пакетов devkitPro и pacbrew из среды разработки недоступны, поэтому финальное слово за CI.

- PS4: нули вместо статических данных. create-fself, закреплённый в pacbrew, считает размер сегмента данных только до конца секции .data, а стандартный link.x вливает в неё лишь *(.data). Секции .data.*, .tdata.* и .tbss.* (статики inline-функций, __libc и stdout/stderr из musl, данные libc++) на консоли читаются нулями. Исправлено своим скриптом линковки cmake/ps4-link.x. Это затрагивает и pPlay: даже лаунчер PS5 терял __libc и TLS локали. Для pPlay подготовлен такой же патч (скрипт для pPlay и лаунчера плюс проверка секций в CI).

- libtorrent не умеет забывать куски. У disk_interface нет способа сказать «куска больше нет», а ошибка чтения в read_piece переводит весь торрент в ошибку. Патч 0006 добавляет torrent_lost_piece(): хранилище сообщает о вытесненном куске, торрент снимает отметку, шлёт пирам lt_donthave и качает кусок снова, когда он нужен. В режиме RAM качаются только окна вокруг позиции стрима и края файла, как в TorrServer; соединения с сидами держатся (close_redundant_connections выключен), иначе «завершённый» между окнами торрент теряет сида.

- ☒ Названия — P2Play (приложение) и MediaMesh (протокол и сеть).

## Дополнение: будущая эволюция HTTP API

Исходный документ фиксирует временную MatriX/Silo-совместимость ради
перехода существующих клиентов. Это переходный слой, а не конечный контракт.
Ближе к завершению разработки совместимость с обоими семействами TorrServer
routes будет удалена. Останется собственный компактный API P2Play с явным
версионированием в URL (например, `/api/v1/...`). Нужные сущности и операции
будут выбраны по фактическим функциям ядра и клиентов; неиспользуемые
MatriX/Silo маршруты и алиасы будут удалены. Переход выполнять после миграции
pPlay, web UI, embedded API и внешних интеграций; до этого compatibility shim
не ломать.
