# Обложки торрентов: извлечение, кэш и API

Обновлено: 2026-11-27. Документ описывает серверную механику обложек P2Play: откуда
берётся картинка для торрента, где она лежит, что отдают маршруты `/api/v1` и как этим
должен пользоваться pPlay, чтобы не заводить второй кэш.

## Зачем

Клиент при добавлении торрента часто не имеет постера: магнет-ссылка его не несёт,
`.torrent` тоже, а `torrs://`-карточка содержит постер не всегда. TorrServer в этом
случае сам ищет картинку в раздаче. P2Play делает то же и отдаёт результат по своему
версионированному API, поэтому веб-интерфейс и внешний клиент видят одинаковую обложку.

Порядок источников (первый успешный выигрывает, дальше не идём):

1. **Постер, присланный клиентом.** Поле `poster` в `POST /api/v1/torrents`,
   `PUT /api/v1/torrents/{hash}`, каталог MediaMesh, pPlay/Silo. Такой постер
   принадлежит клиенту и **никогда** не заменяется серверной картинкой; извлечение для
   такого торрента не запускается вовсе.
2. **Файл-картинка внутри торрента.** Кандидаты по имени (без учёта регистра и пути):
   `poster.*` (100), `cover.*` (95), `folder.*` (90), `front.*` (85),
   `fanart.*`/`backdrop.*` (80), `thumb.*`/`thumbnail.*` (70), `poster…*`/`cover…*` (60),
   затем любая другая картинка (10 — мельче раньше). Расширения: `jpg`, `jpeg`, `png`,
   `webp`, `gif`. Проверяются первые четыре кандидата; файл читается целиком, но не
   больше 2 MiB, и обязан начинаться с сигнатуры JPEG/PNG/WEBP/GIF — иначе берётся
   следующий.
3. **Кадр видео через ffmpeg.** Если картинки в торренте нет, а `ffmpeg` есть в `PATH`
   и настройка `CoverProbe` включена, сервер берёт самый большой видеофайл и просит
   `ffmpeg` снять кадр (`-ss 30`, при неудаче `-ss 0`), масштаб `480:-2`, JPEG.
   Чтение идёт через собственный потоковый маршрут по loopback (см. ниже), поэтому
   работает и в RAM-режиме, и в дисковом, и не требует полной загрузки файла.
4. **Ничего.** Отрицательный результат запоминается, чтобы не тянуть торрент заново
   при каждом старте.

## Границы и лимиты

| Параметр | Значение |
|---|---|
| Размер исходной картинки | до 32 MiB (larger — не кандидат) |
| Размер сохранённой обложки | до 2 MiB, как poster в MediaMesh |
| Чтение картинки | до 64 кусков, таймаут куска 90 с |
| Ожидание метаданных | 120 с на задание |
| ffmpeg | таймаут 45 с, два прохода (`-ss 30`, `-ss 0`), JPEG ≤ 2 MiB |
| Очередь заданий | 64 хеша, одно задание за раз |
| Платформы с ffmpeg | Linux и Android (fork/exec); Switch/PS4/PS5 — только картинки из торрента |

Извлечение идёт в отдельном потоке `m_coverThread` и никогда не выполняется на
HTTP-потоке или в колбэке libtorrent: торрент без пиров ждёт метаданные сколько угодно,
а API обязан отвечать. Торрент на время извлечения активируется штатным `add()`, после
чего закрывается обычным idle-таймером.

## Кэш на диске

Всё лежит в каталоге данных ядра (у встроенного режима pPlay это
`<данные pPlay>/p2play_embedded/`):

```
<data>/covers/<infohash>.img    картинка как есть
<data>/covers/<infohash>.json   {"source","type","bytes","at"}
<data>/covers/<infohash>.none   отрицательный результат {"reason","at"}
```

* `source` — `torrent:<имя файла>` или `probe`.
* Кэш привязан к `infohash`, а не к пользователю: обложка — метаданные раздачи, как
  название и категория.
* Файл `covers/*` удаляется, когда торрент исчезает из библиотек всех пользователей
  (`Core::remove` → `Core::coverForget`).
* `.none` живёт до `POST`/`DELETE` маршрута обложки; причину можно прочитать в
  `covers/<infohash>.none` и в логе `[Cover:<hash>] none: …`.
* На старте в очередь ставятся все библиотечные торренты без постера; задания с
  готовым `.img` или `.none` сразу отбрасываются, так что второй старт ничего не
  качает.

## API

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/torrents/{hash}/cover` | Обложка торрента из библиотеки пользователя. `200` — байты картинки, `Content-Type` из кэша, `ETag`, `Cache-Control: private, max-age=86400`, `X-P2Play-Cover: <source>`. `304` при совпадении `If-None-Match`. `404` + `X-P2Play-Cover: none`, если обложки нет. |
| `DELETE /api/v1/torrents/{hash}/cover` | Убрать закэшированную обложку и отметку `.none`. `200 {"status":"dropped"}`. Повторное извлечение не запускается. |
| `POST /api/v1/torrents/{hash}/cover` | Извлечь обложку сейчас (кнопка «Refresh cover»). `202 {"status":"extracting"}`; `409`, если у торрента есть постер клиента. |

Поля карточки в `GET /api/v1/library/torrents` и `GET /api/v1/torrents/{hash}`:

```json
{
  "poster": "",                       // постер клиента, если он был
  "cover": true,                      // есть серверная обложка в кэше
  "cover_source": "torrent:poster.png" // или "probe"
}
```

Байты обложки **не** инлайнятся в выдачу библиотеки: список отдаёт только флаг, а
картинку клиент забирает отдельным запросом (и получает `304`, если она у него уже
есть). Это же правило держит `Content-Security-Policy` страницы: `img-src 'self'`,
внешние постеры не вставляются.

Доступ — та же cookie/Bearer-сессия, что и у остальной библиотеки. Публичного
постер-URL без авторизации нет.

## Внутренний поток для ffmpeg

`ffmpeg` не читает торрент сам: сервер поднимает запрос к своему же маршруту
`GET /api/v1/torrents/{hash}/files/{index}/stream` по `127.0.0.1` и передаёт заголовок
`X-P2Play-Internal: <token>`.

* Токен случайный, 64 hex-символа, живёт один запуск процесса, не пишется на диск и не
  логируется.
* Принимается только от `127.0.0.1` и только на маршрут потока (`internalStreamPath`
  проверяет форму пути). Ни один другой маршрут `/api` этот заголовок не понимает.
* Даёт права `owner` только на чтение выбранного файла — ровно то, что нужно кадру.

## Как этим пользуется pPlay (чтобы не было двойного кэша)

* **Встроенный режим (`P2Play_embedded`).** Кэш обложек уже лежит внутри каталога
  данных pPlay, в `p2play_embedded/covers/`. pPlay не должен копировать эти байты в
  свой `data/cache/posters`: он читает файл по пути
  `<данные pPlay>/p2play_embedded/covers/<infohash>.img` или отдаёт его через
  `P2Play::coverPath(hash)`. Один файл — один владелец.
* **Внешний сервер.** Файлов чужой машины у pPlay нет, поэтому там работает обычный
  `PosterCache` по ключу вида `p2play-cover:<host>:<infohash>`: одна загрузка, дедупликация
  по md5 содержимого уже есть, `ETag`/`304` не даёт качать повторно.
* **Постер клиента главнее.** Если pPlay (или каталог) прислал `poster`, сервер не
  трогает его и не извлекает свою обложку: `cover` остаётся `false`, а `poster`
  отдаётся как раньше. Поэтому «обложка pPlay» и «обложка сервера» никогда не
  сосуществуют для одной раздачи.
* Нельзя считать кэш обложек папкой загрузок: это метаданные, они не участвуют в
  раздаче и удаляются вместе с последней записью библиотеки.

## Проверки

`tools/ui-test.py` поднимает локальный сидер (python-биндинг libtorrent, как в
`tools/meshnet-test.py`) и проверяет: обложку из `poster.png` внутри торрента (байты,
тип, `X-P2Play-Cover`, файл в кэше, поля карточки), `ETag`/`304`, `DELETE`/`POST`
(refresh), `409` при посте anime клиента, отсутствие обложки у торрента без пиров и
кадр видео через ffmpeg (`source: probe`) для торрента без картинок. Без
python-биндинга libtorrent или без ffmpeg соответствующие проверки печатают `SKIP`.

## Пользовательский постер (web-ui)

Пользовательская обложка теперь загружается на узел P2Play и становится
приоритетным источником постера. Исходные байты не остаются внешней ссылкой:
в JSON торрента поле `poster` получает same-origin URL
`/api/v1/torrents/{hash}/poster`, а изображение отдаётся самим P2Play с
обычной проверкой сессии. Формат JSON при этом не меняется: `poster` по-прежнему
строка, как и для существующих клиентов.

* `POST /api/v1/torrents` принимает multipart `poster_file` или поле
  `poster_url` (в JSON либо multipart). Для файла и загруженного URL
  ограничение 2 MiB; сигнатура должна соответствовать JPEG, PNG, WebP или GIF.
* `POST /api/v1/torrents/{hash}/poster` заменяет постер существующего элемента;
  multipart использует `poster_file` или `poster_url`, JSON — `url`.
  `GET` выдаёт сохранённые байты с ETag, `DELETE` удаляет ручной постер и
  возвращает торрент к штатному поиску обложки.
* Файл и метаданные хранятся в общем каталоге `covers/` по infohash. Это не
  каталог загрузок. При удалении последней пользовательской записи торрента
  выполняется существующая очистка кэша обложек.
* Непустой постер устанавливается до фонового извлечения: ручная запись
  сериализована с завершающей записью автообложки, поэтому фоновый поток не
  перезаписывает пользовательское изображение. При наличии ручного постера
  сервер не ищет картинки в torrent-файлах и не запускает ffmpeg.
* URL на этом этапе должен быть публичным IPv4 HTTP-адресом/доменом. Loopback,
  private, link-local и зарезервированные адреса, URL с учётными данными и
  перенаправления на локальные ресурсы отклоняются. HTTPS в текущей сборке core
  не поддерживается (TLS-зависимости отключены); для HTTPS-источников используйте
  загрузку файла из браузера.

## Что ещё не сделано

* Нет лимита размера каталога `covers/` и очистки по возрасту (в отличие от
  `DiskCacheSize` для торрентов).
* `.none` не истекает сам: повторная попытка — только `POST`/`DELETE` маршрута обложки.
* MP4 без `faststart` (moov в конце файла) может не дать кадр на обоих проходах; для
  таких раздач обложки не будет, пока в торренте нет картинки.
* Нет проверки, что найденный «постер» действительно постер раздачи: имя и сигнатура —
  единственные критерии (как в TorrServer).
* ffmpeg-путь не собран для Switch/PS4/PS5: там доступны только картинки из торрента.
