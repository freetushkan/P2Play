# Компактный медиакаталог: policy и выбор списков/шардов

Статус: локальная реализация, ожидает PR/CI. Исходная база — master
`820dbb6424c51c53b2f9a41134bcd5da27149634`. Wire format не меняется.

## Что следует из inventory-report.json

### План по отчёту `d80e86ca-29fe-42fa-85a5-cd1c2f6e6467`

Категория и шард — разные вещи. У Rutor оставляем нативные категории;
объединяем только физическую раскладку `CartoonMovie` + `CartoonSeries` и
`DocMovie` + `DocSeries`. У RuTracker используем те же видеокатегории по
известным forum ID: четыре бывшие группы Movie объединяем в `Movie`.
Отдельный `DocSeries` не назначаем без проверенного соответствия форумов.

| `series` | 4,66 | 6,89 |
| `anime` | 0,74 | 2,72 |
| `cartoons` | ~1,41 | ~3,24 |

Цифры — оценки zlib исходных групп, для объединений показана сумма, а не
результат пересжатия. Пустой `Other` не требует публикации. RuTracker всё
ещё `degraded` (475 690 отклонённых строк). Его 1,19 млн активных записей и
470 352 711 байт NDJSON превышают лимиты полной версии (1 млн строк и 256 MiB
распакованного текста); физические шарды внутри списка этот блокер не снимают.

CSV был виден в предыдущем отчёте (`Video` — 33,7 MiB по оценке zlib), но в
новом завершился `failed` при чтении локальной Git-ревизии. Конкретная команда
из старой диагностики неизвестна. Новый профиль измеряет Anime, предполагаемые
фильмы/прочее видео, UHD/4K (видеопризнак вместе с 2160p/4K/UHD и аналогами)
и музыкальные группы по расширениям в названии. Неоднозначные контейнеры
наподобие M4A не считаем доказательством lossless. CSV не предоставляет список
имён файлов: классификация по названию не доказывает ни тип видео, ни кодек.

`inventory_shard_map` влияет только на отчёт, а не на публикацию. При нескольких
метках строка попадает в один шард по первой сопоставленной категории. В HTML
и JSON для категорий и плановых шардов есть четыре оценки: NDJSON и zlib без
локальных допполей и с ними, плюс частоты реально сохранённых ключей. Вариант
с допполями — модель с вложенным `provenance`, не публикационный формат. Если
извлечение было отключено, исходный объём этих полей не восстановить из отчёта.

Для повторного замера скопируйте обновлённый пример профиля, укажите локальные
пути, включите источники и используйте команду ниже с новой SQLite-базой.
CSV можно отдельно проверить с `--source torrents-csv-data`; если есть только
локальный CSV-файл без Git, укажите `path` вместо `repo`. Цель остаётся 50 MiB
сжатых сегментов на шард (до 70 MiB как исключение после пробного релиза).

Стартовая схема: раздельные списки **Видео** и **Музыка**, а внутри — шарды по
интересам подписчика. Для музыки сначала Lossy/Lossless, дальше Rock, Electronic,

Цель — до **30 MiB** сжатых сегментов каталога на шард, **50 MiB** — верхний
порог для проверки перед релизом. Мерьте фактические сегменты publisher, а
отдельно — manifest/torrent, клиентскую SQLite и media packs. Если семантическая
группа не укладывается, сначала дробите по устойчивой подкатегории, затем по

каждого обновления. Два списка — отправная точка, а не гарантия прохождения
лимитов: до экспорта проверяйте отдельно лимиты **1 млн записей / 256 MiB NDJSON**
на каждый список после классификации и дедупликации. Если не проходят — делите
ещё и списки. Шардирование внутри списка само по себе эти лимиты не снимает.

#### Повторный прогон inventory

1. Скопировать `tools/profiles/catalog-inventory.example.json` в приватный профиль,
   вернуть локальные `repo`/`path` и включить CSV, Rutor и RuTracker. Шаблоны
   сетевых источников оставить выключенными. `forum_include_ids` и CSV-фильтр
   допуска оставлены прежними. RuTracker разбит по явным forum ID, не по regex в
   рантайме. CSV использует `first`: Anime → Video → MusicMixed → MusicLossless →
   MusicLossy → MusicUnknown. M4A/OGG/WMA, AC3/DTS и MQA сами по себе не определяют
   формат; метки по заголовкам — эвристика.
2. Запустить в новый каталог, чтобы не смешивать наблюдения старого профиля:

   ```sh
   mkdir -p "$HOME/p2play-inventory-v2"
   python3 -I tools/grabber.py inventory \
     --profile "$HOME/grabber-profile-v2.json" \
     --state "$HOME/p2play-inventory-v2/inventory.sqlite3" \
     --report "$HOME/p2play-inventory-v2/inventory-report.json" \
     --categories-dir "$HOME/p2play-inventory-v2/categories"
   ```

3. Сначала проверить статус, quarantine и `checkpoint_deferred` по каждому
   источнику. При `degraded` разобрать причины по quarantine, не считать размеры
   финальными. После чистого прогона проверить размеры новых групп, выборки
   Mixed/Unknown/HiResReview и перекрытия по infohash. Складывать размеры
   категорий разных источников как точный размер объединённого шарда нельзя.
4. Только после проверки подготовить пробную публикацию с отдельным состоянием.
   Новый профиль **не создаёт списки и физические шарды**: CSV-группы относятся
   только к inventory; обычный `run` использует группы RuTracker как теги, а
   `publisher.shard_policy` маршрутизирует новые записи по тегам и сохраняет
   прежний шард для известных записей. Экспорт с дедупликацией, маршрутизация CSV
   и перенос существующего каталога — отдельные шаги. Существующий state не заменять.

## Удалённые RuTracker

Inventory пишет `<categories-dir>/<source-id>-deleted.ndjson`, в том числе при
`unchanged`, из сохранённых наблюдений SQLite. В report указан `deleted_file`.
Это локальный диагностический список infohash/topic/forum, не подписанный каталог
и не файл для publisher. Активные метрики и пересечения уже исключают tombstones.
Удаления оставлены в SQLite для аудита: файловый sidecar сам по себе не уменьшает DB.

В обычном `run` tombstone по-прежнему требует старый опубликованный shard.
Неизвестные удаления остаются в quarantine. Нельзя просто выкинуть все `<del/>`:
это может восстановить старую раздачу из CSV/Rutor. Никогда не переносить tombstone
в новый `deleted` shard — подписчик старого shard не увидит удаления.
Полный экспорт уже содержит только live записи; очистка опубликованного каталога
выполняется через проверенный `--replace`, не ручное удаление SQLite строк.

## Группы RuTracker

`tools/profiles/rutracker-media.example.json` — отдельный opt-in стартовый профиль,
не автозамена пользовательского. Он выключен; необходимо задать локальный XML/XZ
и включить source. `forum_include_ids` ограничивает обработку медиаразделами,
`category_groups` задаёт непересекающиеся массивы явных forum ID:
Movie, Series, CartoonMovie, CartoonSeries, Anime, DocMovie, TVShow, Music.

ID собраны из предоставленного отчёта, а не получаются по названиям во время работы.
Профиль консервативный: исключены архивы, книги, ПО, игры, аудиокниги, спортивные,
учебные и музыкальные видеoразделы. Music включает обычную музыку, рок, поп,
электронику, джаз/блюз, Hi-Res/оцифровки и Apple music, но не весь раздел Apple Audio.
Это стартовый выбор оператора, не полная экспертная разметка всех 1344 форумов.

В mixed документальных форумах нет надёжного признака Movie/Series: они пока
отнесены к DocMovie; **DocSeries автоматически не угадывается**. Названия некоторых
корневых форумов также неоднозначны. Перед публикацией проверить группы на реальных
выборках; для точного соответствия Rutor потребуется более детальная классификация.
Неизвестный ID не получает выдуманную группу. В обычном run он сохраняет исходную
категорию, если разрешён `forum_include_ids`; inventory всегда сохраняет native
forum ID/name, независимо от настроенных групп. Рядом теперь выводится дополнительная
сводка `category_group_summary`: active/deleted, with/without size и payload bytes
по `category_groups`, плюс отдельный остаток `ungrouped`. Пустые группы видны.
Сводка строится по сохранённому `provenance.forum_id`, не по названиям форумов,
и доступна также для отключённого/невыбранного cached источника без чтения XML.
Текущие правила применяются только к имеющимся наблюдениям: прежние фильтры
и возраст данных сохраняют значение. Исходная форумная таблица не заменяется.

## Дополнительные поля и размер

RuTracker source:

```json
"extra_fields": {
  "description": false,
  "history": false,
  "duplicate_hints": false
}
```

По умолчанию все три включены для обратной совместимости. `false` отключает
извлечение/нормализацию и сохранение соответствующих данных provenance; XML всё
равно читается и декомпрессируется целиком. Базовые поля записи совпадают с моделью
Rutor: ih/title/date/size/files/tags/trackers. В текущем адаптере content не был
подписанным description_ref: основная экономия здесь — локальная DB/CPU, а не
клиентский media download. Topic ID, forum, даты и tracker ID остаются для аудита.
Эти опции не являются глобальным удалением медиа из других источников или overrides.

Отпечаток политики включён в CSV/RuTracker checkpoints. Изменение групп, фильтров,
порядка CSV групп или extra_fields вызывает пересканирование того же файла.
Чистый inventory scan заменяет старые данные источника. В обычном run отсутствующие
в новом snapshot наблюдения намеренно сохраняются; это не автоматический garbage
collector. Для полностью компактной базы использовать новую inventory DB и затем
осознанную пересборку публикации. Backup старой DB обязателен.

## CSV: Video / Music

Пример профиля использует `inventory_category_mode: "first"`: первая подходящая
группа выигрывает. Video проверяется до Music, так что `x264 AAC` — только Video,
а `Album FLAC` — Music. Без настройки сохраняется legacy режим `all`.
Это эвристика заголовков, не доказательство музыкального содержимого: отдельные
аудиодорожки с AAC/DTS могут попасть в Music. Неизвестные названия не маркируются
автоматически. Title filters по-прежнему определяют допуск строки.

Группы относятся к inventory: существующий контракт не переносит эвристические
CSV группы в publisher tags. Физический экспорт двух публикуемых CSV каталогов
остаётся отдельным шагом после проверки классификации, не скрытым side effect.

## Списки или шарды

| Механизм | Для чего | Цена для конечного клиента |
| --- | --- | --- |
| Список | Независимый владелец/ключ, расписание, политика доверия, отдельный крупный каталог | Отдельные pointer, manifest, version torrent, подписка и discovery |
| Шард | Выбор категорий в одном каталоге одного владельца | Общий pointer/manifest/torrent; payload невыбранных record segments не скачивается |
| Мета-список | Витрина независимых каталогов | Ещё одна metadata подписка; не заменяет shard selection |
| Media pack | Опциональные описания/постеры | Ленивый fetch и отдельный бюджет; не раздувает поисковый индекс описаниями |

Стартовый план списков и шардов по актуальному inventory приведён выше.
Не создавайте по копии каталога на каждый трекер: источник лучше хранить в
локальном provenance, а пересечения проверять по infohash.

Если владелец, обновления и аудит одинаковы и manifest остаётся малым, один список
с video/music shards проще: меньше сетевых сущностей и единая дедупликация infohash.
Это рабочая альтернатива для небольшого deployment. Дробление на сотни форумов не
рекомендуется: растут manifest, число файлов и стоимость каждой версии, даже если
record payload выборочный. Поиск сейчас локальный по выбранным загруженным данным;
новые списки/шарды сами по себе не улучшают алгоритм поиска.

Перед выбором окончательной схемы измерить на одинаковой выборке: compressed
records, manifest/torrent bytes, SQLite и RSS клиента, cold start, subscribe,
search p50/p95, объём малого delta update и поведение selective restart.
Сравнить один список с shards и два списка с теми же записями. Существующий CI
baseline 20 000 записей в `media-shards.md` не доказывает масштабируемость на
1.8 млн. Действуют лимиты grabber/publisher: 1 млн записей и 256 MiB NDJSON;
профиль с группами не отменяет их и не создаёт автоматически два списка.

## Покрытие источников

Inventory JSON/HTML дополнен таблицей покрытия каждого источника объединением
остальных: active, covered, процент, exclusive. Удаления не учитываются ни с одной
стороны; тройное пересечение не суммируется дважды. Для пустого источника процент
не определён (`null` / «—»). Используются все сохранённые inventory в SQLite,
включая ранее загруженные, невыбранные и отключённые: это сравнение накопленных
данных, а не только текущего refresh. Поле `source_coverage_scope` явно задаёт охват.
Без `--source` уже обрабатываются все enabled из профиля; это покрыто тестом.

## Уточнение отчёта: matrix, Category / Other, размер

Таблица покрытия теперь N×N: A,B = доля live infohash источника A, найденных
в B. При трёх источниках — 3×3. Диагональ 100%, пустые строки — «—».
Основная RuTracker таблица показывает Category, Included forums, активные/удалённые,
размеры раздач и каталог NDJSON / zlib estimate. Other идёт последним, исходные
форумы сохранены в раскрываемых деталях. Relative count убран: он показывал лишь
численность относительно максимальной категории.
Размер NDJSON точен для сохранённых нормализованных записей с newline, сжатый
размер — оценка Python zlib level 6, сегменты до 8 MiB. Это не финальный SQLite и
не точный размер публикации: portable C++ encoder протокола отличается. MediaMesh
действительно сжимает record segments zlib, но packs хранят raw bytes. Итоговые
manifest/torrent/packs/index и JSON publisher измеряются после публикации отдельно.

## Все источники и Anime

Единая Category-сводка с размерами теперь применяется ко всем адаптерам; форумный
счётчик для CSV/Rutor — «—». Other последним, исходные категории в details.
Отключённые источники скрываются из всего HTML даже при наличии кэша, пустые —
тоже. JSON сохраняет диагностику, visible_totals согласован с HTML; SQLite не чистится.
Anime: native Rutor, forum-ID rules RuTracker, отдельная первая CSV-группа по
явным anime/аниме/fansub markers в примере профиля. Это консервативная эвристика,
не полное распознавание. Пользовательские профили нужно обновить вручную.
